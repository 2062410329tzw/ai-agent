# 复盘与下一步

## 最难的问题

难点不是让模型说出“30天”，而是让它在看到另一个“15天”时继续找证据、承认制度关系未知，并给出真正支持回答的引用。正常路径成功不能证明冲突路径成功，代码中一个固定if也不能证明模型在决策。

真实联调证实了这一点：早期备用模型能识别期限不同，但遗漏正文引用标记，在收到笼统校验反馈后重复同样输出，最终到达步数上限。项目保留了这次失败，而不是在代码里把结果改写成成功。改进为具体的引用修复反馈，并在提示词结尾强调一次一个动作、冲突后补查、正文引用格式。随后真实模型完成了读取双方、补查、追问的路径。

## 实际改进

1. 检索：首轮Mock验收9/10。资料外问题补查“制度”时，被“员工、制度”两个通用词误召回。加入停用词后同一离线验收10/10；此改进只能证明固定合成集上误召回减少，不能宣称检索准确率全面提升。
2. 引用：结构上限制引用只能来自本轮实际读取，并验证版本、原文连续性和正文标记；校验错误反馈给模型，由它修正。
3. 模型服务：遭遇网络限制与主模型HTTP429；确认主模型供应商错误码1305（过载）。显式切换配置测试其他Flash模型，失败记录单独保留，没有把服务失败替换成Mock成功。
4. 复现：每例保存当时知识库快照和哈希，变更30天为45天时能追溯到实际资料；新增独立脚本核对Trace、引用与快照一致性。
5. 口语与范围：真实模型曾正确读到30天，却自行扩展成财务审核/付款期限问题并误报资料不足。提示词增加仅回答用户实际所问、口语映射及已有依据时结束的规则；检索增加显式主题过滤，并测试跨主题的优先级通知仍会保留。失败保存在live-retry/paraphrase，完整修复回归保存在live-v1。

## 学习收获的归属

以上是本轮AI辅助开发过程观察到的工程经验，不冒充候选人的个人感悟。候选人应亲自复跑并补充自己遇到的问题、理解变化和修改内容，详见AI使用说明。

## 取舍与尚未完成部分

原生循环便于解释每一步，也减少环境依赖；词法检索在小语料上易验证，但需要更多真实表达覆盖。未完成生产级权限、企业真实资料接入、大规模语义评测、自动通用冲突证明、完整提示注入防护和Linux上的真实模型联调。它们与本题核心交付的必要程度不同，不能把未实现项写成已完成。项目已发布到用户指定GitHub仓库，Ubuntu上的离线CI通过，见交付记录。

下一步优先级：先由候选人独立复核实际回答；再扩充独立测试集，加入跨部门范围、明确替代关系、否定句、多文档组合和更多口语；以固定预算比较词法/向量召回及重排，再决定是否引入额外服务。优化模型JSON稳定性与空检索收敛速度，应保留对比记录而非仅展示成功样例。

实际开发与验证用时见评估文档；模型等待计入本轮经过时间，没有把AI生成时间虚构为候选人手工开发时间。
